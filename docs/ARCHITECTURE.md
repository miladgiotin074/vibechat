## اصل اصلی مقیاس‌پذیری: سرورهای اپ بی‌حالت‌اند

- **هیچ وضعیتی در حافظه‌ی سرور اپ نگه داشته نمی‌شود** جز سوکت‌های همان نمونه. هر رویداد (پیام، مچ، لایک…) با `PUBLISH u:<userId>` در Redis منتشر می‌شود و هر نمونه‌ای که سوکت آن کاربر را دارد، آن را تحویل می‌دهد. پس سوکت‌ها **sticky session لازم ندارند** و Load Balancer کلادفلر می‌تواند آزادانه پخش کند.
- آپدیت‌های ربات با webhook به `POST /bot/webhook` می‌آیند؛ هر سرور می‌تواند پاسخ دهد. پیام‌های خروجی ربات در صف `bot` می‌روند و محدودیت سرعت تلگرام (۲۵ پیام در ثانیه) **در Redis و سراسری** اعمال می‌شود؛ اضافه‌کردن worker هرگز از سقف تلگرام عبور نمی‌کند و با خطای 429 کل صف به‌اندازه‌ی `retry_after` مکث می‌کند.
- تنظیمات زنده‌ی پنل با Pub/Sub فوراً به همه‌ی نمونه‌ها می‌رسد.
- مایگریشن‌ها با advisory lock اجرا می‌شوند؛ بالا آمدن هم‌زمان چند سرور امن است.

## مسیرهای پرترافیک

**ورود:** مینی‌اپ `initData` امضاشده‌ی تلگرام را می‌فرستد ← سرور HMAC-SHA256 را با توکن ربات بررسی می‌کند (و تاریخ آن را) ← کاربر اگر نبود ساخته می‌شود (ثبت‌نام خودکار) ← JWT یک‌ساعته + refresh token چرخشی. هر بار باز شدن اپ دوباره با initData وارد می‌شود؛ هیچ فرم ورود یا رمزی وجود ندارد.

**احراز هویت هر درخواست:** بررسی امضای JWT + یک `MGET` در Redis (وضعیت کاربر و ابطال نشست). کاربر مسدود فوراً `403` می‌گیرد و سوکتش بسته می‌شود.

**کشف (سوایپ):** هر کاربر یک صف `deck:<id>` در Redis دارد (۱۰۰ نفر). وقتی کم شد، `findCandidates` با ایندکس‌های جزئی فقط کاربران قابل نمایش را از جدیدترین فعال‌ها اسکن می‌کند (حداکثر ۱۰۰۰ ردیف، مستقل از اندازه‌ی شهر)، شرط دوطرفه‌ی جنسیت و سن، مسدودها و سوایپ‌شده‌ها را حذف می‌کند و رتبه‌بندی می‌کند: بوست، کسانی که لایکت کرده‌اند، **تازه‌واردها (۴۸ ساعت اول)**، تأییدشده‌ها، فعال‌های اخیر، امتیاز جذابیت. مینی‌اپ چند کارت جلوتر نگه می‌دارد و عکس‌ها را پیش‌بارگذاری می‌کند، پس سوایپ هیچ‌وقت منتظر شبکه نیست.

**سوایپ و مچ:** درج با `ON CONFLICT DO NOTHING` ← بعد از commit، بررسی لایک متقابل (دو لایک هم‌زمان هم را از دست نمی‌دهند) ← ساخت مچ با `ON CONFLICT (user_a, user_b)`. شمارنده‌های لایک دریافتی در Redis جمع و هر ۲ دقیقه دسته‌ای در Postgres نوشته می‌شوند؛ هیچ سوایپی ردیف کاربران را قفل نمی‌کند.

**پیام:** یک تراکنش (درج پیام + به‌روزرسانی `matches` و `match_members`) ← `PUBLISH` برای هر دو طرف ← اگر گیرنده آنلاین نبود، پیام تلگرامی ربات (حداکثر یکی در هر ۱۰ دقیقه برای هر گفتگو). `client_id` یکتا ارسال تکراری را بی‌اثر می‌کند.

## پایگاه داده (`apps/server/migrations/001_init.sql`)

| جدول | نکته |
|---|---|
| `users` | شناسه UUIDv7. `telegram_id` یکتا (بعد از حذف حساب NULL می‌شود تا بتواند دوباره ثبت‌نام کند). `can_dm` / `bot_blocked` برای اعلان‌های ربات، `ref_code` برای دعوت، `bonus_superlikes`، `activated_at` برای دیده‌شدن تازه‌واردها. ایندکس‌های جزئی کشف + GiST برای فاصله |
| `referrals` | یک ردیف برای هر کاربر دعوت‌شده؛ `qualified` وقتی پروفایلش را کامل کرد (جایزه‌ی دعوت‌کننده همان موقع داده می‌شود؛ حساب‌های خالی جایزه نمی‌گیرند) |
| `swipes` | **۳۲ پارتیشن hash** روی `swiper_id`، بدون کلید خارجی؛ ایندکس جزئی «چه کسی لایکم کرده» |
| `matches` + `match_members` | دو ردیف عضویت برای هر مچ ← فهرست گفتگوها یک range scan؛ شمارنده‌ی خوانده‌نشده در همین ردیف |
| `messages` | **۳۲ پارتیشن hash** روی `match_id`؛ `client_id` یکتا |
| `payments` | پرداخت تتراپی؛ `token` درگاه یکتا؛ تسویه با `UPDATE … WHERE status = 'pending'` ← callback، webhook و بررسی دوره‌ای هر چقدر هم هم‌زمان برسند، فقط یک‌بار اعتبار می‌دهند |
| `notifications` / `announcements` | اعلان شخصی / اطلاعیه‌ی همگانی (یک ردیف برای همه، با گزینه‌ی ارسال از ربات) |
| `photos`, `blocks`, `reports`, `plans`, `admins`, `audit_logs`, `app_settings`, `daily_stats` | مثل پروژه‌ی قبلی |

## رشد و جذب کاربر (Viral loop)

1. **لینک دعوت اختصاصی** برای هر کاربر: `t.me/<bot>/<app>?startapp=r_<code>`. دوست دعوت‌شده بلافاصله ۳ سوپرلایک هدیه می‌گیرد؛ دعوت‌کننده وقتی دوستش پروفایل را کامل کرد ۳ سوپرلایک و هر ۵ دعوت موفق ۷ روز عضویت ویژه (همه از پنل قابل تغییر).
2. **اشتراک‌گذاری بومی تلگرام:** «ارسال برای دوستان» (share sheet)، «کارت دعوت در چت» (inline mode ربات: تایپ `@bot` در هر چتی کارت دعوت با لینک خود کاربر می‌سازد)، «استوری کن» (Story با ویجت لینک).
3. **وقتی لایک یا سوپرلایک تمام شد**، کنار عضویت ویژه، دعوت دوستان به‌عنوان راه رایگان پیشنهاد می‌شود.
4. **ثبت‌نام دو مرحله‌ای ۲۰ ثانیه‌ای:** جنسیت + سن، سپس عکس (عکس پروفایل تلگرام خودکار گذاشته می‌شود) و نام (از تلگرام پر شده). بقیه‌ی پروفایل بعداً.
5. **تازه‌واردها ۴۸ ساعت اول در کشف بالاتر می‌آیند** تا زود لایک و مچ بگیرند (مهم‌ترین عامل ماندگاری).
6. **اعلان‌های ربات = Push:** مچ جدید، پیام وقتی آفلاینی، «یک نفر لایکت کرد» (با فاصله‌ی ۳ ساعت)، هدیه‌ی دعوت، و پیام «دلمون برات تنگ شده» برای غایبان (ساعت ۱۸ تهران، حداکثر هفته‌ای یک بار) با دکمه‌ای که مستقیم به صفحه‌ی مربوط در مینی‌اپ باز می‌شود.
7. **چت تصادفی** برای وقتی که هنوز مچی نیست.

## مسیر رشد ظرفیت

| مرحله | توپولوژی | تقریباً |
|---|---|---|
| ۱ | یک سرور (۴–۸ هسته، ۸–۱۶ گیگ): `--profile data --profile app`، ۲–۴ نمونه‌ی API | تا ده‌ها هزار کاربر فعال روزانه |
| ۲ | یک سرور داده (Postgres + Redis) + ۲ تا N سرور اپ پشت **Cloudflare Load Balancer** (health check روی `/health`)، فایل‌ها روی R2 | صدها هزار |
| ۳ | PgBouncer (transaction mode، `DATABASE_PGBOUNCER=true`)، replica خواندنی Postgres برای آمار پنل، Redis جدا برای صف‌ها و Pub/Sub، سرورهای worker جدا | میلیون‌ها |

نکات:
- مجموع اتصال‌ها: `DATABASE_POOL_MAX × تعداد نمونه‌های API و worker` باید زیر `max_connections` بماند؛ در غیر این صورت PgBouncer.
- جدول‌های `swipes` و `messages` از ابتدا ۳۲ پارتیشن دارند؛ همه‌ی کوئری‌ها کلید پارتیشن را دارند.
- WebSocket پشت Cloudflare: کلادفلر سوکت بیکار را بعد از ۱۰۰ ثانیه می‌بندد؛ مینی‌اپ هر ۲۵ ثانیه ping می‌زند و در صورت قطع با backoff وصل می‌شود و آنچه از دست داده را دوباره می‌گیرد.
- Cloudflare Load Balancer: یک pool با همه‌ی سرورهای اپ، monitor روی `https://api.<domain>/health`، steering «Least outstanding requests» یا «Random»، **Session affinity لازم نیست**.

## امنیت و حریم خصوصی

- اعتماد فقط به `initData` امضاشده (HMAC با توکن ربات، با انقضا). در حالت توسعه `DEV_FAKE_TELEGRAM` فقط خارج از production کار می‌کند.
- Refresh token چرخشی که فقط hash آن ذخیره می‌شود؛ استفاده‌ی دوباره از یک token قدیمی کل نشست را باطل می‌کند.
- عکس‌ها دوباره کدگذاری و بدون متادیتا (GPS) ذخیره می‌شوند؛ پیش‌نمایش تار با کلید تصادفی جدا.
- موقعیت با دقت ~۱ کیلومتر، فقط فاصله‌ی گردشده نمایش داده می‌شود. آیدی تلگرام فقط به مچ‌ها و فقط با اجازه‌ی کاربر.
- پرداخت: وضعیت آدرس بازگشت درگاه هرگز معتبر حساب نمی‌شود؛ فقط پاسخ `verify` با تطابق `order_id` و مبلغ. webhook هم فقط به‌عنوان «این token را دوباره verify کن» استفاده می‌شود.
- فایروال سرورهای اپ فقط ترافیک 80/443 را از IPهای کلادفلر می‌پذیرد.
